# План проверки методов WB API для аналитики

Дата составления: 2026-05-05.

## Цель

Issue #7 просит проверить, какие методы Wildberries подходят для оперативной сводки за текущий день и текущую неделю. Финансовые отчёты полезны для закрытой экономики периода, но для текущей недели они могут возвращать неполные данные или не отдавать данные до закрытия отчёта.

Этот документ фиксирует план проверки, чтобы реализация аналитики не опиралась на предположения.

## Проверяемые блоки

| Блок | Основной вопрос | Ожидаемый источник |
|------|-----------------|--------------------|
| Баланс | Можно ли обновлять при каждом открытии Dashboard | `GET https://finance-api.wildberries.ru/api/v1/account/balance` |
| Карточки | Есть ли полный набор идентификаторов для последующего сопоставления | Content API справочники и `POST /content/v2/get/cards/list` |
| Остатки FBY | Как быстро формируется отчёт и какие склады приходят в JSON | `warehouse_remains` task API |
| Остатки FBS | Достаточно ли chrtID из карточек для запроса по всем складам | `/api/v3/warehouses` и `/api/v3/stocks/{warehouseId}` |
| Розничные цены | Какой актуальный метод раздела "Цены и скидки" возвращает цену по nmID | Требует проверки по текущей документации WB |
| Заказы | Есть ли сегодняшние и недельные данные | Методы Statistics / Marketplace orders |
| Выкупы / продажи | Можно ли отделить продажи от заказов и связать с nmID / srid | Методы Statistics sales |
| Отказы / возвраты | Где появляются операции возврата и отказа до закрытия финансового отчёта | Методы Statistics / Reports с типом операции |
| Финансы | Какая задержка у реализации и эквайринга | `sales-reports` и `acquiring` |

## Протокол тестирования

1. Подготовить WB-токен продавца с доступом к Контенту, Маркетплейсу, Статистике, Аналитике и Финансам.
2. Запускать проверки отдельно для периодов: сегодня, текущая неделя, прошлая неделя.
3. Для каждого метода сохранять обезличенный лог ответа: URL, метод, status, duration, request id, shape ответа, ключевые поля.
4. Не сохранять токен, персональные данные продавца и полные коммерческие значения в репозиторий.
5. Сравнить наличие идентификаторов `nmID`, `chrtID`, `barcode`, `vendorCode`, `srid`.
6. Зафиксировать лимиты, retry-поведение и наличие rate-limit заголовков.
7. Обновить `docs/Backlog.md` точными методами для заказов, выкупов, отказов и возвратов.

## Критерии выбора методов для Dashboard

- Метод отдаёт данные за сегодня или текущую неделю.
- В ответе есть идентификатор товара для связи с кэшем карточек.
- Метод можно вызывать по расписанию без превышения лимитов WB.
- Ошибки и пустые периоды можно отличить друг от друга по статусу или структуре ответа.
- Для финансовых сумм метод имеет понятную задержку и может быть сверлен с закрытым финансовым отчётом.

## Вывод для реализации

Dashboard должен использовать два слоя данных:

1. Оперативный слой: баланс, заказы, продажи / выкупы, отказы, возвраты и остатки из методов, которые дают текущий период.
2. Финансовый слой: закрытые отчёты реализации и эквайринга, обогащённые товарным кэшем и дополненные пользовательскими расходами для расчёта чистой прибыли.
